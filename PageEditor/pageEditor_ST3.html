Feedback Page

Technical Description

HTML Structure
The Feedback page reuses the shared <header>, navigation and <footer> from the site template, with everything page-specific inside <main>.

  • A <section class="directory-section"> holds a <div class="section-heading-row"> (the heading plus a sort <select>) and a <div class="programme-scroll" tabindex="0"> wrapping six <article class="card programme-card"> items, each with an icon <img>, a heading, a description and a call-to-action link.
  • A <section class="reviews-section"> holds a ratings summary and three review <article> cards.
  • The form itself is a <form id="feedbackForm" novalidate> split into two <fieldset>/<legend> groups ("Personal Details" and "Feedback Details"), using text, email, tel, date and datetime-local inputs, a <select>, and a <textarea maxlength="300">.
  • Each field has a matching <span class="error-msg" role="alert"> for inline validation feedback, and a live <p id="charCounter" aria-live="polite"> reports the remaining character count.


CSS Techniques
Layout
  • The shared .card-grid is CSS Grid by default, so .programme-scroll .programme-grid overrides it to display: flex with width: max-content, letting the six programme cards line up in a single horizontally scrollable row (overflow-x: auto plus scroll-snap-type: x mandatory) instead of wrapping into a tall grid.
  • Flexbox lays out the ratings summary (the large numeric score beside its label and description) and each .form-row (label, input and error stacked vertically).
  • Fixed positioning is used site-wide for the "Go to Top" button, defined once globally in style.css rather than repeated per page.

Styling
  • CSS variables from :root keep colours, spacing and shadows consistent with the rest of the site.
  • A .has-error class, toggled by JavaScript, applies a red border and background to any invalid field.
  • .confirmation-msg:not(:empty) means the confirmation box's background and border only appear once the script has actually written a message into it, so it takes up no visual space beforehand.
  • The programme "Join"/"Get Involved" buttons get an extra hover effect (colour change plus scale(1.06)) on top of the site-wide button hover, for stronger feedback in a horizontally scrolling context.


JavaScript
The form's interactivity is provided by a <script> embedded at the end of the body, and covers three things: a live character counter that updates the aria-live counter as the user types in the message field; custom validation on submit that checks each required field (name, a regex-checked email format, a regex-checked phone format, address, programme selection, visit date, and message) and writes a specific error message into that field's error span while toggling .has-error; and, on success, a confirmation message written into #confirmationMsg and the form reset. If validation fails, the script moves keyboard focus to the first invalid field, so a keyboard or screen-reader user lands directly on the problem rather than having to search for it.


Accessibility

The two <fieldset>/<legend> groups give screen readers explicit context for each group of inputs. Every field has an explicit <label for="..."> tied to its input's id. Both the character counter and the confirmation message use aria-live="polite" so updates are announced without moving focus, while error messages use role="alert" so a failed submission is announced immediately. Invalid fields are marked with both a red border and red text, not colour alone, so the error remains clear to users who cannot distinguish colour easily.

Team Page

Technical Description

HTML Structure
The team is presented as a <section class="team-grid" aria-label="Team members"> containing four <div class="team-card" tabindex="0" role="group" aria-label="..."> blocks.

  • Each card holds an avatar <img>, an always-visible .team-basic block with the member's name and role, and a .team-details block with their full name, role, and a short contribution summary that is hidden until the card is hovered or focused.
  • The tabindex="0", role="group" and descriptive aria-label on every card mean a keyboard or screen-reader user can identify each team member without depending on the hover-revealed content alone.


CSS Techniques
Layout
  • The four cards sit in a responsive CSS Grid: grid-template-columns: repeat(auto-fit, minmax(240px, 1fr)).
  • The reveal panel animates open with a max-height: 0 → 260px transition combined with :hover, :focus and :focus-within, so it triggers on mouse hover, direct keyboard focus, and focus landing on anything nested inside the card.

Styling
  • The thumbnail gets a combined opacity, scale() and saturate() change on the same trigger, for layered visual feedback that the card is interactive.
  • A visible outline appears on :focus to satisfy the keyboard focus-state requirement.


JavaScript
No JavaScript is used on this page. The hover/focus reveal, the thumbnail feedback, and the focus outline are all handled entirely through CSS transitions and pseudo-classes.


Accessibility

:focus-within was included specifically so the reveal still works when focus lands on a link or button nested in the card rather than the card element itself. Each member's name uses an <h2> rather than an <h3>, since, after the page's own <h1>, the four team members are the primary content of the page. Every card is reachable and operable by keyboard alone, with a clearly visible focus outline distinguishing the selected card.

Content Page – Protecting Ecosystems

Technical Description

HTML Structure
The article follows the shared template exactly, with a <nav class="toc-nav" aria-label="Page contents"> placed at the top of .main-content, listing anchor links to each of the page's seven <section class="content-section" id="..."> blocks.

  • Each section uses its own <h2> (and <h3> where a topic splits into sub-points), semantic <figure>/<figcaption> pairs for four supporting images, and a two-column .figure-pair layout for the restoration comparison.
  • Three .myth-box callouts present the "myths" section as a bold claim followed by a short rebuttal.
  • The "Go to Top" button uses the same shared <span id="top"></span> plus fixed .go-top anchor pattern used across the whole site, defined once in style.css.


CSS Techniques
This page's styling is written as an embedded <style> block in the <head> rather than a separate external stylesheet, which the coursework explicitly allows as an alternative to a linked file.

Layout
  • .toc-nav ol uses CSS multi-column layout (columns: 2, collapsing to one column under 600px) to keep a seven-item contents list compact.
  • .figure-pair uses CSS Grid: one column by default, switching to two columns above 700px for the Protected Areas / Community-Led Restoration comparison.

Styling
  • Every .content-section has scroll-margin-top so that clicking a contents link doesn't leave the target heading hidden behind the sticky site header.
  • Images use a soft double border (a surface-colour border plus a thin outline), a box-shadow, and max-width: 100% for full responsive sizing.
  • One in-text link in the "What You Can Do" section carries an inline color: blue; text-decoration: underline; style, since it sits in plain body text with no wrapping class – without it, the shared a { color: inherit; text-decoration: none; } reset would make it invisible as a link.


JavaScript
No JavaScript is used on this page. The in-page contents navigation, the responsive figure layout, and the "Go to Top" button are all implemented in plain HTML and CSS.


Accessibility

The multi-column contents list gives readers a fast way to jump to any of the seven sections without scrolling past all of them first. scroll-margin-top is a small addition, but without it every anchor jump would leave the target heading hidden behind the header. Heading levels never skip (h1 → h2 → h3), and every image has descriptive alt text rather than a generic caption or filename.

Challenges and Lessons Learned

Keyboard Accessibility on the Team Page
An early version of the expandable member cards only responded to :hover, so the extra detail was invisible to anyone navigating by keyboard. Adding :focus and :focus-within to the same rule, alongside tabindex="0" on each card, fixed this so the interaction is now consistent across input methods.


Overriding a Shared Grid on the Feedback Page
Making the programme cards scroll horizontally instead of wrapping meant overriding the shared .card-grid (CSS Grid) rule inside the scrollable rail. My first attempt kept the cards wrapping into rows because the grid rules were still winning. Explicitly setting display: flex and width: max-content on the more specific .programme-scroll .programme-grid resolved the conflict.


Invisible Links on the Content Page
The shared a { color: inherit; text-decoration: none; } reset meant a plain in-text link had no visible affordance at all until I added an inline colour and underline to it directly. The lesson from all three issues was to always check computed styles in browser dev tools when a shared class or rule doesn't behave as expected in a new context, and to test interactive features with the keyboard alone, not just the mouse.


Compliance

The Feedback, Team, and Content pages I created comply with JANET's Acceptable Use Policy in the following ways:

  • Original and appropriate content: All written text on my three pages was authored by me for this coursework. None of it is defamatory, obscene, or offensive, and all of it is directly relevant to the ClimACT website's SDG 13 purpose.
  • Responsible use of external resources: Programme icons, team avatars, and content-page images are stored locally within each page's own folder (Feedback/Images/, Team/images/, ContentPage/images_ST3/). Any image not created by me personally will be properly credited in the References section before final submission, and any real photographs of teammates will only be used with their consent – no unauthorised or unlicensed third-party material has been published.
  • No unauthorised data collection: The Feedback form does not transmit data to a server or third party. Its JavaScript calls event.preventDefault() on submit specifically so the form never leaves the browser – no personal data entered by a visitor (name, email, phone, address) is ever stored, shared, or retained anywhere.
  • No security risk: The site contains no external form submission endpoints, no third-party scripts beyond Google Fonts, and no code that could compromise a visitor's device or data.
  • Academic integrity: All technical descriptions in this Page Editor describe my own implementation work; where I referenced external documentation (MDN, module lecture notes) to inform my approach, those sources are credited in the References section.
